## The problem, stated as a user hits it

targ caches the compiled build-tool binary and rebuilds when its inputs change — including any local `replace` target's contents, so editing targ's own source invalidates the cache. `filepath.WalkDir` never follows symlinks, so that contract breaks silently wherever a symlink stands between the walk and the source:

- **The replace target is a symlink** (`replace … => ../targ-link`, the normal way to share one checkout across projects). `os.Stat` follows links so the directory looks present; `WalkDir` yields the link itself and descends no further.
- **A symlinked directory sits inside a hashed tree.** Reported as a non-directory, contents never read. This applies to the module's own files as much as to replace targets, because both go through `collectModuleFiles`.

Either way: you edit source, the hash does not change, targ reruns the previously cached binary, and nothing says so. Every diagnostic instinct blames your own code first.

Measured, not assumed (scratch probe, this session):

| tree | `os.Stat` | `WalkDir` entries |
| --- | --- | --- |
| real directory | ok, `isDir=true` | 3 (`real`, `pkg`, `a.go`) |
| symlink to it | ok, `isDir=true` | **1** (the link) |
| symlinked subdir inside a walked tree | — | reported `dir=false`, never descended |

**#31** is a different problem in the same loop: in release mode the replace target *is* targ's directory inside `GOMODCACHE` — immutable by construction, verified by hash, never mutated in place — and it gets walked and hashed on every invocation to detect a change that cannot happen.

## Design notes

- **Where cycle detection lives.** `collectModuleFiles` becomes a thin wrapper over a recursive walker carrying a `visited map[string]bool` keyed by **resolved real path** (`filepath.EvalSymlinks`). Before descending into any directory — the root, or a symlinked entry — the walker resolves it and returns immediately if the resolved path is already in the set. This terminates on self-loops (`a/link -> a`), ancestor loops (`a/b/link -> a`), and mutual loops (`x/link -> y`, `y/link -> x`), and it also deduplicates diamonds (two links to one directory) so content is hashed once.
- **Keying the visited set by resolved path is what makes it correct.** Keying by the logical path would never collide, so it would not detect cycles at all — the loop `a/link/link/link/…` presents an unbounded sequence of distinct logical paths.
- **Symlinks may point outside the module, and that is the point.** A replace target's whole purpose is to reference a checkout elsewhere on disk, so the walker must not restrict traversal to the module subtree. The cost is that a nested link to a very large tree will be walked; the cycle guard bounds loops but not size. This is accepted — it mirrors what the Go toolchain can reach through the same links — and is called out here so it is a known property rather than a surprise.
- **`entry.IsDir()` is false for symlinks**, which is exactly why the current code misses them. Detection must test `entry.Type()&fs.ModeSymlink != 0` and then resolve; a symlink to a *file* should be read like any other includable file, a symlink to a *directory* recursed into.
- **Existing filters must survive.** `skipIfVendorOrGit` and `isIncludableModuleFile` apply identically to symlinked content — a symlinked `vendor/` is still skipped, a symlinked `.go` file still included.
- **#31's own open question is resolved: plain skip is safe.** The issue offers "skip the walk **or** hash path+version". Skip loses no coverage: `writeIsolatedGoMod` (`:4332-4362`) embeds `dep.Version` in the synthetic go.mod, which `collectModuleFiles(importRoot)` hashes independently at `:2488`. A version change still changes the key with zero contribution from `collectReplaceDirFiles`.
- **#29's unreachable-target branch has a template two lines away.** The loop already hashes a marker rather than erroring when a directory is missing: `TaggedFile{Path: "replace-missing:" + dir}` (`:2602-2607`), commented "Hash the absence so the key still changes when the dir appears." A dangling symlink is the same situation and must adopt that contract — the #37 cycle's regression came from a new path inventing its own error behaviour instead of its sibling's.
- **#30 is an add-on, not a batch member.** It shares no function with the others (same file only) and is included because its value peaks now: it pins file-set-change detection through `collectModuleFiles` at the moment that function is being rewritten.

```go
// collectModuleFiles hashes every source file reachable from moduleRoot,
// following symlinks. WalkDir alone does not descend into symlinked
// directories, so a shared checkout referenced through a link would
// contribute nothing to the cache key and edits to it would never trigger a
// rebuild. Traversal is guarded by a visited set keyed on the resolved real
// path, which terminates symlink cycles and also hashes a directory reachable
// by two paths only once.
func collectModuleFiles(moduleRoot string) ([]discover.TaggedFile, error) {
	return collectModuleFilesFrom(moduleRoot, map[string]bool{})
}
```

The recursive helper must:
1. `filepath.EvalSymlinks` the directory it is entering; on failure return `(nil, nil)` — unreachable is not fatal here, matching the caller's marker convention.
2. Return early if the resolved path is already in `visited`; otherwise mark it. **Key on the resolved path** — keying on the logical path detects no cycles at all, since `a/link/link/…` is an unbounded sequence of distinct logical paths.
3. `filepath.WalkDir` the resolved directory, preserving the existing `skipIfVendorOrGit` and `isIncludableModuleFile` filters and the existing read/append behaviour.
4. In the callback, detect symlinked entries with `entry.Type()&fs.ModeSymlink != 0`: resolve; if it is a directory, recurse with the same `visited` map and append the results; if it is a regular file and includable, read and append it.
5. Keep output deterministic — `WalkDir` is lexical, and recursion happens at a deterministic point, so no sort should be needed; verify by running the tests twice and comparing, and add a sort only if order proves unstable.

Then in `collectReplaceDirFiles`, resolve the target before use and route a dangling link to the existing marker branch rather than a new one:

```go
		resolved, resolveErr := filepath.EvalSymlinks(dir)
		if resolveErr != nil {
			// Unresolvable target — same as a missing one: hash the absence so
			// the key still changes when it appears.
			files = append(files, discover.TaggedFile{Path: "replace-missing:" + dir})

			continue
		}
```
…and stat/walk `resolved`. The marker keeps the ORIGINAL `dir`, since that is the configured path whose appearance must change the key.
